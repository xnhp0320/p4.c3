# 基于静态顺序与运行时布局的 header 重构：与 SWX 的比较

日期：2026-09-28。本文评估讨论中的候选方案，供结合 [SWX 源码分析](swx-parser-deparser-internals.md) 继续推敲；尚未形成实现决定、语义 spec 或 roadmap。项目仍以自己的简易前端和 DPDK 上的 P4 → C codegen 为当前方向，也保留直接生成 C3 的可能。

## 1. 结论与证据边界

**这个方案有明确的优化空间，最直接的是中间 header 增删时，只移动受影响的前缀，以及把新 header 的字段直接写进报文。** SWX 已经使用原包 header view、相邻区间合并和部分零复制路径；因此，收益需要来自比这些机制更进一步的程序分析和专用代码生成。

需要同时保留三个判断：

- 静态证明顺序兼容，可以把一类通用构包问题收敛为有序区间的增删和移动，减少运行时选择与 scratch 使用。
- 运行时 ctx 随 action 更新、在 action 边界进行物理重构，是可行的实现方向；每个 action 都立即重构，却不保证整个 pipeline 的总成本更低。
- 顺序证明只能解决部分问题。字段值的来源、旧版本的存活、条件 emit、循环区域和 buffer 条件，仍然决定能否安全原位操作。

本文中的 **SWX 事实**以 DPDK 提交 `4f795ddd6a1fbdea97b7b254dea6d8f1f837a681` 为准。复制计数来自已有的 [helper 局部实验](../research/swx-codegen/README.md)，不是完整 SWX 或 DPDK 的性能测量；该实验在 macOS 上运行提取的原始 helper，使用缩减结构和字节数组，没有运行真实 mbuf、端口、解释分派或 SWX codegen 链路。**本方案的成本均为推导，尚未实现或测量。** 本文也不据此主张对全部已有工作的原创性。

## 2. 对方案的准确表述

### 2.1 编译期：建立可以共享的顺序

1. 分析 parser 各路径的 extract 次序，建立 header 实例之间的顺序约束。
2. 分析 deparser 各路径的 emit 次序，汇总可能出现的顺序约束。
3. 对能够证明兼容的部分，求公共拓扑顺序。
4. 依据该顺序和程序中 header/区域的数量，确定 packet ctx 中固定槽位的组织方式。
5. 为各 action 的布局变化生成专用代码；只有编译期无法消除的信息才保留为运行时状态。

### 2.2 运行时：ctx 随 packet 穿过各表而变化

Parser 把实际出现的 header 绑定到对应槽位，记录位置、实际长度和有效性。随后，表 action 对 header 的激活、失效、字段修改等操作，持续改变 ctx 中的逻辑状态和布局信息。

**这个数组是 packet ctx 的运行时数据结构，不是仅在编译期存在的排序结果，也不是只能在最终 deparser 才使用的 emit 清单。** 固定槽位不意味着固定物理地址；发生重构后，槽位必须反映当前报文的位置。

### 2.3 Action 边界：提前完成物理重构

对于新增 header，可以在 action 内计算字段值，在选定的提交点移动旧 header、腾出空间，并将新字段直接写入此次提交确定的位置。后续表通过更新后的 ctx 访问这些 header；之后的 action 仍可能再次改变布局。

这可以避免一份完整的独立新 header 存储及其后续复制。少量字段仍可能暂存在 C 局部变量或寄存器中；它不意味着完全没有临时值。若依赖允许，也可在 action 更早的位置预留空间并直接写入。

最终 deparser 仍承担逻辑上的输出选择和顺序要求。若前面已完成所需布局，它的物理工作可能缩减为确认输出范围和更新发送信息；若还有条件输出等未决事项，仍需最后一次调整。

## 3. SWX 已经做了什么，差异在哪里

SWX 的基本执行路径是指令解释器，见 [instr_exec](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline.c#L7783)；可选 C codegen 将指令组原生化并接回其执行框架，见 [指令组代码生成](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline.c#L14402)。下面比较的是其实际 header helper 和构包机制，不能将解释器分派成本与构包算法成本混为一谈。

| 维度 | 固定版本 SWX | 本方案的潜在差异 |
| --- | --- | --- |
| Parser extract | 建立指向原包的 view，记录长度、推进 cursor | 同样可以零整头复制；进一步消除不必要的描述符访问、生成专用边界检查和字段访问 |
| Header 状态 | 指针表、有效位、header 描述符 | 按静态分析生成的槽位，附带当前布局和必要的变化信息 |
| 新 header | validate 时使用预先分配的 header 存储，随后填字段 | 条件允许时直接在 packet buffer 中构造 |
| setInvalid | 修改有效位，不立即压缩报文 | 在 action 提交时可删除对应空间并更新当前布局 |
| emit | 跳过 invalid，追加来源区间，合并相邻来源 | 公共顺序可提前确定；实际输出选择仍需遵守程序分支 |
| 重构时机 | 通常到 TX 的 emit_handler 才物理构包 | 可以分布在 action 边界，最终 deparser 补齐未决变化 |
| 简单构包 | 原布局/前缀删除可零复制；特定前缀新增只复制新头 | 这些场景部分持平；新头直接构造还可能省去暂存后复制 |
| 其他构包 | 先把输出 header 汇集到 scratch，再整体复制到 payload 前 | 为中间增删生成局部 memmove，保留无需移动的区间 |
| 重排 | 通用 gather 路径可以处理相应区间顺序 | 第一类快速路径先排除重排，后续补充局部重排和回退 |

源码入口：[extract helper](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline_internal.h#L1987)、[emit helper](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline_internal.h#L2165)、[validate/invalidate](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline_internal.h#L2341)、[emit_handler](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline_internal.h#L1754)。

还有两个比较时容易遗漏的事实：

- SWX 的 header 存储与输出 scratch 在 [header_build](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/pipeline/rte_swx_pipeline.c#L1515) 中按执行上下文预分配，并非每个 packet、每次 extract 都 malloc。这里的收益主要是减少存储和复制，而不能笼统表述为消除了逐包堆分配。
- SWX 的上述构包路径也把输出放在 parser 剩余 payload 前，保留 payload 原位置。固定 payload、利用其前方空间并不是本方案独有的部分；更具体的区别是如何选择需要移动的 header，以及何时直接写入新字段。

因此，值得继续研究的组合是：**P4 程序级顺序与值来源分析 → 专用布局计划 → 与字段写入融合 → 合适时机的原位提交。** 运行时保留 ctx 数组不意味着必须采用指令解释执行。

## 4. 顺序分析：成立条件与保守性

### 4.1 判断公共顺序，应检查两个图的并集

节点首先应代表 header **实例**，例如 `outer_ipv4` 和 `inner_ipv4`，不能仅按 header 类型合并。先考虑每个实例只有一个活跃物理来源、每次输出至多出现一次的情形：

```text
Gp：某条可能的 parser 路径中，A 与 B 均出现且 A 在 B 前 → 加边 A→B
Ge：某条可能的 deparser 路径中，A 与 B 均发射且 A 在 B 前 → 加边 A→B
G = Gp ∪ Ge
G 无环 → 存在满足两组约束的公共拓扑顺序
```

应检查并集是否无环。仅检查两个图分别无环、或者只查直接的反向边，可能遗漏跨图组成的长环。证明无环前，它们是顺序约束图；Hasse 图/传递约简属于后续表示选择。

“忽略 if/else”应理解为保守汇总路径上的约束，不能把互斥分支拼成一条执行序列：

```text
emit A; if (condition) emit B; else emit C; emit D;

约束：A→B→D，A→C→D
不存在仅由这段程序推出的 B→C 或 C→B
```

这个判断是**充分但保守的证书**。例如 parser 和 deparser 都在同一稳定条件下选择 AB 或 BA，每次执行可能完全同序，但汇总得到 A↔B，无法得到一套适用于所有路径的公共顺序。未来可以对条件分类生成不同计划；存在静态环不等于每个 packet 都发生重排，也不等于程序不合法。

### 4.2 名字同序仍不足以证明字节来源同序

假设 A、B 同类型，control 执行逻辑值交换：

```text
tmp = A; A = B; B = tmp;
deparser: emit A; emit B;
```

即使 parser 与 deparser 的实例名都是 A、B，输出内容的来源已经互换。实现可以选择把值写回原槽位，也可以改绑定，但前者本身需要保存旧值，后者需要处理物理重排。

所以顺序分析必须配合值来源/别名/存活分析，或者明确将这类程序分到另一条路径。需要逐步分开四个概念：实例身份、字段值版本、物理来源区间、emit 的出现次数。相关值语义见 [P4 header 操作](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-ops-on-hdrs)。

### 4.3 Parser 的环可以归并，但归并的是布局区域

对于 TLV/option 循环，可以把 parser 控制流图中的强连通分量总结为一个区域 R，使外层继续分析 `A → R → B`。运行时记录 R 的起点和动态长度，必要时在 R 内保留最后一次 extract 对应的逻辑 header view。循环次数并不必然要求 ctx 按次数扩张。

但有两项必须单独成立：

1. **消费区域与逻辑值分开。** 同一变量多次成功 extract 后，该变量持有最后一次提取的值；parser 实际消费的字节则包含此前各次。发生后续字段赋值时还要跟踪赋值结果。参见 [P4 extract](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-packet-data-extraction)。
2. **归并不自动改变输出语义。** 输入为 `A T1 T2 T3 B payload`，若最终仅 emit 保存最后一个 TLV 的 `h`，不能因为把循环归并成 R，就输出 T1、T2、T3 全部字节。若实际程序用一个包含整个区域的 varbit header 表达 R，或扩展语言明确规定保留 R，才能按整体保留。

区域内可以“整体保留”“只保留最后的逻辑值”或“按内部计划修改”，外层统一使用区域接口。区域内部 view 与区域本体引用相同字节，不能在长度求和时重复计数。存在多入口、多出口、同一逻辑变量在区域外继续 extract 等情况时，还需核对区域边界与值来源，不能只合并节点就结束分析。

尤其要区分三种图：

| 图 | 环的含义 | 处理方式 |
| --- | --- | --- |
| Parser 控制流图 | 状态循环、重复消费输入 | 总结为动态布局区域，并保留内部语义 |
| Parser/deparser 顺序约束图 | 无法证明单一公共顺序 | 条件化分析，或进入重排路径 |
| 物理移动依赖图 | 写入会覆盖尚未读取的来源 | 改变调度、拆分区间或使用 scratch |

将第二种环收缩为一个节点，可以定位问题区域，不能因此声称区域内部的重排已经解决。

## 5. 运行时数组需要维护什么

### 5.1 至少区分四种状态

| 状态 | 需要回答的问题 |
| --- | --- |
| 来源 | 字段值来自哪次 extract、哪次赋值或新构造？ |
| 逻辑 validity | 当前 P4 header 是否 valid？ |
| 当前物理布局 | 字节目前是否位于工作报文中，位置与长度是什么？ |
| 输出选择 | 当前执行路径是否会 emit 这个值、发射几次？ |

例如 B 一直 valid，但 deparser 写 `if (flag) emit(B)`。仅维护 setValid/setInvalid 的变化，不能决定最终是否要从输出中删除 B。反过来，某个 header 不在最终输出中，但后续表还要读取它，也不能提前销毁它的唯一存储。

因此 action 边界维持的是**当前可供后续处理使用的工作布局**。当最终输出选择已经可确定时，它可以直接与输出布局一致；尚未确定的内容需要保留或在后续提交点处理。

### 5.2 建议的信息模型

以下是分析所需的信息，不要求逐项成为运行时 struct 字段：

```text
每个固定槽位：instance_id / region_id
              valid、当前存储位置、实际长度
              必要的来源/值版本、变化标记
每个 packet：当前报文起点、payload 锚点、长度、存储可写与容量条件
编译期：     公共 rank、固定字段布局、各 action 的影响范围
必要时：     独立的输出 occurrence 列表和旧值临时存储
```

静态 rank 与实例身份应解耦。第一类路径中可以恰好按 rank 排列槽位，但新增/删除不必移动数组元素；改变槽位状态和字节位置即可。以后需要重排时，可以生成另一条槽位访问序列。

坐标也必须明确：地址、相对 buffer 起点的偏移、相对当前 packet 起点的偏移，不能混用。报文起点前移后，一个 header 的绝对位置可以不变，但 packet-relative offset 已变化。每次实际移动之后，后续读取必须使用更新后的 view；此前保存的裸指针和按旧地址生成的 table key 不能无条件沿用。

Parser 消费终点应独立记录。`advance`、重复 extract 中被覆盖的早期内容、仅供解析的 header 都可能形成不输出的字节区间，因此不能通过“当前 valid header 长度之和”重新推算 payload 起点。

## 6. 无重排时，怎样生成局部重构代码

### 6.1 固定 payload，从后向前确定目标位置

先限定一类清晰的情形：按字节操作；待改动的 header 区域连续、可写；空间足够；保留的旧字节没有其他必须保存的活跃别名；payload 保持在原位置。记：

```text
P   = payload 起点，使用 buffer 坐标
L_i = 此次提交要物理保留/构造的第 i 个区间长度
O   = Σ L_i
S'  = P - O                         提交后的报文起点
dst_i = P - Σ(j >= i) L_j           第 i 个区间的目标起点
```

这里的集合由本次工作布局决定，不能直接拿全部 valid header 代替。首轮解析后可能存在间隙，应该使用实际 `src_i`；在后续已经紧凑排列的布局中，可以进一步用前后长度差简化偏移计算。

例一：删除 B。

```text
原包： [ A ][    B    ][ C ][ payload ]
新包：          [ A ][ C ][ payload ]
       A 向右移动 |B|，C 与 payload 保持原位
       报文起点向右移动 |B|
```

实现是 `memmove(src_A + |B|, src_A, |A|)` 加起点/长度更新。即使 A 与 B 长度不同也成立；含义是移动 A 到新前缀位置，不要求恰好覆盖原来 B 的整个区间。

例二：在 A、B 之间插入 X。

```text
原包：       [ A ][ B ][ C ][ payload ]
新包： [ A ][ X ][ B ][ C ][ payload ]
       A 向左移动 |X|，X 直接写入腾出的空间
       B、C 与 payload 保持原位
```

这些变换中，插删位置影响的是其前方的前缀。维护 ctx 时可以根据静态影响范围更新，而不必无条件调整全部槽位。

### 6.2 一个 action 提交点的候选步骤

1. 计算决定有效性、长度、字段值所需的表达式，保留仍需读取的旧值。
2. 得到此次工作布局，计算目标位置；检查容量、连续性、所有权和整数溢出等条件。
3. 在破坏原布局之前确定可以成功执行，或进入预先定义的回退路径。
4. 按安全顺序移动仍然需要的旧字节；能合并的相邻区间合并。
5. 将新字段直接写到目的地，并融合不再需要复制旧字节的覆盖写。
6. 更新受影响的 ctx view、报文起点/长度和必要的 DPDK 发送元数据。

这是数据与内存依赖允许时的顺序，并非要求把所有表达式都提前到 action 开头。Extern 调用、字段读取和条件判断的可观察顺序仍须保持；处理 `return`、control `exit` 等路径时也必须让后续状态一致。所谓“提交”是编译器安排布局同步的位置，不自动赋予 action 事务或回滚语义。

### 6.3 同序区间可以避免重排 scratch 的一个充分条件

设保留的源区间互不重叠且依次排列，目标区间也互不重叠且保持同序，每个保留区间的源/目标长度相等，并且不存在其他需要保存的旧值或别名。则可采用：

- 向左移动的区间，按源位置从左向右处理。
- 向右移动的区间，按源位置从右向左处理。
- 新增区间在受影响的旧来源已安全保存或移动后再写入。

理由是：向左移动只可能覆盖更靠前的源；若更靠前的区间静止或向右移动，目标同序且互不重叠的条件又排除了该覆盖。因此需要先处理的只会是更靠前的左移区间，右移情况对称。单次调用内部的重叠由 memmove 处理。

这给出了这一受限问题的可执行策略，并非所有构包情形的最优性证明。Header 变长、重复发射、整头赋值或区域内部改写，需要先拆成满足条件的字节区间，或使用更一般的规划。

### 6.4 数组维护也有成本

若每次 setValid/setInvalid 都重算全部 H 个槽位，U 次变化可能产生 O(UH) 的元数据工作。可以先记录 action 内的变化，在 action 结束时扫描一次，仍然实现“每个 action 提交”，不必等到最终 deparser。

进一步可根据静态分析，仅更新受影响的槽位，把固定偏移直接生成常量，或者把几个连续区间合并为一次移动。通用扫描、专用分支和代码体积之间的平衡需要测量；复制字节减少可能被大量 ctx 读写抵消。

## 7. 与 SWX 的具体复制成本对比

设 `a=|A|`、`b=|B|`、`c=|C|`、`x=|X|`，所有输出后面都有同一段 payload。旧 header 值均不变，X 为新构造的 header，各 buffer 条件满足。

下表只计 **SWX emit_handler 的 memcpy 请求字节数**，以及本方案候选计划中 **旧字节的移动量**。新字段写入单列；不包含 parser、字段计算、ctx 更新、原先在 SWX 暂存区填字段的成本。一次长度 N 的 memcpy 计 N，而不是把读和写计成 2N。

| 布局变化 | SWX 构包复制 | 本方案移动旧字节 | 本方案直接写新字段 | 判断 |
| --- | ---: | ---: | ---: | --- |
| ABC → ABC | 0 | 0 | 0 | 已有零复制路径，基本持平 |
| ABC → BC | 0 | 0 | 0 | 前缀删除可只调起点，基本持平 |
| ABC → AC | 2(a+c) | a | 0 | 只右移 A，C 不动 |
| ABC → AB | 2(a+b) | a+b | 0 | AB 右移 c，省去 scratch 往返 |
| ABC → XABC | x | 0 | x | SWX 还需先在独立存储填 X；直接构造可省去之后的 x 复制 |
| ABC → AXBC | 2(a+b+c+x) | a | x | 只左移 A，并直接构造 X |
| ABC → AXBC → ABC，跨两个 action | 最终布局不变时为 0 | 若两次立即提交，为 2a | 中间写 x | 提前提交可能输给延迟构包 |

SWX 通用路径的 `2O` 来自输出 header 先 gather 到 scratch，再将长度 O 的结果复制回 packet。它不会因此复制整段 payload。表中前缀新增命中特定两区间快速路径；如果输出来源不满足该条件，需要重新判断路径。

已有实验使用 `a=4, b=8, c=4, x=4`：

| 单次变化 | SWX helper 实测请求字节 | 本方案按上述计划推导 |
| --- | ---: | --- |
| ABC → AC | 16 | 移动 4 字节 |
| ABC → AB | 24 | 移动 12 字节 |
| ABC → XABC | 4 | 旧字节移动 0，直接写 X 的 4 字节 |
| ABC → AXBC | 40 | 移动 A 的 4 字节，直接写 X 的 4 字节 |

SWX 数据见 [results.txt](../research/swx-codegen/results.txt)。本方案对应列没有执行实验。上述差距说明存在算法层面的复制优化空间，不能据此换算吞吐倍数；小尺寸复制的内联、分支、cache、寄存器压力和描述符访问都可能改变实际结果。

### 7.1 提前提交的反例应成为设计输入

例如 table 1 插入 X，table 2 又删除 X，最终输出与输入完全相同。立即重构会把 A 左移、再右移；延迟构包有机会完全省掉这两次移动。SWX 仍可能付出 X 的字段计算和暂存写入成本，不能把最终 emit 零复制解释成整条 pipeline 零成本。

因此需要把两种决定分开：

- **如何移动**：同序增删时采用局部原位计划。
- **何时移动**：action 边界是候选提交点，也可以依据后续使用和观察边界合并某些提交。

如果后续 action 必须立即获得新头的连续物理地址，或 extern 观察报文布局，提前提交有实际价值。如果后续只读少数字段，暂存几个标量、稍后一次提交可能更便宜。这里存在“更早物化”与“减少重复搬移”的权衡，无法单靠拓扑顺序解决。

## 8. 方案本身需要处理的问题

| 问题 | 最小反例或风险 | 设计上需要保留的处理方式 |
| --- | --- | --- |
| Valid 不等于 emit | B 有效，但 `if (flag) emit(B)` 只在部分路径执行 | 保留输出选择；在条件确定后调整布局 |
| 值被复制后还有旧版本 | `saved=A; A.f=v;`，后面还读取 saved | 保存活跃旧值、按需复制，或使用独立存储；不能共享可变指针冒充值复制 |
| 同一头多次 emit | `emit(A); A.f=v; emit(A);` | 输出 occurrence 与值版本分离；未支持时明确诊断，不能只保留一条槽位记录 |
| setValid 被重复调用 | 已 valid 的头再次 setValid | 不应再次插入一份物理 header；validity 变化与存储构造分开 |
| 新字段尚未获得完整定义 | 新头部分字段有值，其他字段由后续 action 填写 | 记录可用值与必要存储，不能凭 setValid 推断所有字节已可读 |
| 布局变化导致旧地址失效 | 前一 action 移动 A，后一表仍用旧指针抽 key | 更新 view、重新获取地址，或采用稳定 base 加当前 offset |
| 循环/varbit 区域 | 逻辑最后一个 TLV 与整个消费区域长度不同 | 同时保留区域边界与内部逻辑 view；区域整体/局部修改分别规划 |
| 位宽与实际长度 | header 含非字节对齐字段，或 varbit 长度运行时变化 | byte 快速路径需要适用条件；位拼接、长度变化另行 lowering |
| 连续性与可写性 | header 跨 mbuf segment，或底层 data buffer 被共享 | 检查并进入局部复制、私有化或其他明确回退 |
| 提前修改的可观察性 | extern 观察包长/原始字节，或保留指针 | 定义 extern 的观察与生命周期契约；在合适边界同步，禁止无证明的移动 |
| 发送元数据失配 | 物理长度改变，但 offload/header-length 等仍旧 | 按目标契约更新相关元数据，并保持校验和处理语义 |
| 优化收益被管理成本抵消 | 每次 valid 变化全量重算 ctx | 编译期折叠、合并提交、更新受影响范围，并测量总成本 |

上表引用的 emit 值版本问题来自 [P4 deparser 语义](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-deparse)。这不直接意味着 p4c → SWX 对上述所有程序都有错误；仍需检查其目标支持范围与上游转换。我们自己的前端也可以从明确受限的子集开始，但应能识别边界。

### 8.1 DPDK headroom 的准确含义

Headroom 是数据 buffer 内、当前 packet data 起点之前的预留空间，能够用于新增字节；它与 `rte_mbuf` 的元数据字段、private area 是不同位置。运行时 ctx 可以另选存放位置，不能把构包消耗的 headroom 与 ctx 元数据混为一谈。参见 [DPDK mbuf 文档](https://doc.dpdk.org/guides/prog_guide/mbuf_lib.html)。

对固定 payload 的策略，所需输出前缀必须能容纳在 payload 前方的可写范围内。还要核对首段长度等约束。Payload 本身可以仍位于后续 segment；支持这类情况不必以复制整个 payload 为前提，但待移动 header 跨段时，需要不同操作。

容量和所有权检查必须在破坏活跃来源之前完成。空间不足不宜无条件退化为通用 malloc；可以选择池中另一个 mbuf、局部 scratch 或目标支持的分段构造方式，具体选择留待目标接口设计。资源失败路径也必须有清楚行为。

## 9. 为未来 header 重排保留空间

### 9.1 保留公共顺序快速路径，分开身份与输出序列

建议接口上允许以下三种情况共存：

| 情况 | 顺序证明/实际情况 | 可能的生成方式 |
| --- | --- | --- |
| 公共同序 | 全局公共顺序已证明 | 固定槽位/常量 rank，加局部增删代码 |
| 条件化同序 | 全局约束有环，但按条件可分成若干同序情形 | 编译多个专用计划，运行时根据条件选择 |
| 实际重排或未能进一步证明 | 某些来源的输出顺序确实改变，或分析不足 | 对相应区域建立输出序列，使用更一般的移动计划 |

不需要因此给所有 packet 增加一张 O(H²) 的动态顺序矩阵。可以继续使用稳定槽位，在冲突路径上额外保存或生成 `emit occurrence → 槽位/值版本/长度` 的序列。简单路径的序列可以完全是编译期常量。

发生过提前重构之后，一般路径必须读取 **当前** 来源坐标；不能再假定 header 仍在最初 extract 的地址。这是 ctx 对后续所有 planner 都要提供的不变量。

### 9.2 局部重排根据物理覆盖关系调度

对每个保留区间生成概念上的移动 `M_i: src_i → dst_i`。如果 M_i 的目标覆盖 M_j 尚未读取的来源，则加依赖 `M_j → M_i`；同一操作自身的重叠由 memmove 处理。

- 依赖图无环：按拓扑顺序移动。
- 存在依赖环：先保存足以打破环的活跃来源，再继续移动；也可以拆分区间。
- 新字段写入与旧字段覆盖写也需要服从来源存活关系。

这套分析与 parser/deparser 的逻辑顺序图用途不同。源区间重复引用、字段版本和变长区域会使依赖更复杂，不能只根据 header 名字建立移动边。

### 9.3 `AB → BA` 不要求新分配整包

对相邻、连续、可写的两个区间，保存较短一段、memmove 另一段、恢复暂存段即可交换顺序：

```text
scratch 大小：min(a, b)
移动请求字节：a + b + min(a, b)
```

对于 `ABC → BAC`，C 和 payload 可以保持不动。与本次 SWX 通用路径的 `2(a+b+c)` 相比，这提供了局部重排的候选方向；也不承诺任何尺寸下都更快。小常量区域还可能使用寄存器或专用 load/store。

上述公式仅适用于这个相邻交换例子。任意重排不能据此推断“一个最大 header 的临时区总够用”。冲突区域还可能因目标位置覆盖其他来源而扩大，必须根据实际区间闭合，而不能只圈出逻辑图中成环的几个 header。

### 9.4 回退机制与直接 codegen 相容

规划器可以表达保留、移动、写入、暂存、更新描述符等操作，最终生成直接 C/C3 或调用专用 helper。这些是编译器内部的规划概念，不要求为它们建立一个逐包 opcode 解释器。

当局部调度太复杂或不划算时，可以只重建 header 区域到有界 scratch，再放回 payload 前；这与 SWX 的通用方式类似，但可以保留外围已经稳定的区间。Buffer 容量或所有权不满足时，再进入不同存储路径。

这使后续功能可以逐步覆盖复杂程序，同时让已证明的同序路径保持简单。无法证明适用快速路径时，应进入已支持的回退；若暂未实现该功能，则给出明确诊断，不应悄悄按同序处理。

## 10. 后续如何判断它是否真正优于已有方案

以下是待验证的问题集合，不安排实施阶段或时间；roadmap 仍由项目讨论决定。

### 正确性需要验证的边界

- 用简单的参考构包模型对照：原字节、逻辑字段结果、最终 validity、实际 emit 序列与剩余 payload。
- 覆盖无变化、前/中/后增删、多处增删、变长区域、循环最后值、条件 emit、字段值复制和实际重排。
- 既检查最终报文，也检查 action 边界之后的读取结果，尤其是 table key 和 extern 所见内容。
- 在支持范围内检查空间不足、共享 buffer、跨 segment、短包和提前退出等分支；不能只检查正常发包结果。
- 验证移动计划保留所有仍活跃的来源；仅验证单次 memmove 没有越界不够。

### 性能比较需要分离的因素

可分别比较 SWX 解释执行、SWX 可选原生加速，以及自有直接 codegen；同时给同一组构包操作做独立比较，以区分分派差异与布局算法差异。测试应在能够实际运行 DPDK 的环境完成，现有 macOS helper 实验不能替代它。

除吞吐/周期外，至少记录：每包移动请求字节、ctx 读写量、布局提交次数、scratch 占用、生成代码体积，以及不同 packet/header 长度下的结果。特别加入“跨 action 增删抵消”与“新头马上被使用”两类负载，评估提交策略。

需要回答的核心问题是：

1. 哪些真实程序能够被证明为公共顺序？保守分析会错过多少可优化路径？
2. 减少复制后，剩余瓶颈是否转移到 ctx 更新、字段访问或 table lookup？
3. Action 边界提交在什么条件下获益，什么条件下应合并或延迟？
4. 循环区域需要整体保留、最后值输出、内部编辑中的哪些能力？
5. 发生重排时，局部计划与通用 header scratch 的实际分界在哪里？

## 11. 本次评估建议保留的设计取向

保留你的三个核心点：**静态分析公共顺序、固定规模的运行时布局数组、在合适的 action 边界直接重构。** 其中有实质优化空间的是专用局部移动和新字段直接构造，尤其适用于最终需要保留的中间 header 插删。

同时给模型补上三个边界：**逻辑 header 与物理区间分离，移动方法与提交时机分离，公共顺序与局部重排路径分离。** 这样可以继续沿简易前端直接 codegen 的方向推进，也能为条件 emit、循环区域和未来重排保留空间。

目前可以确认的是复制成本存在下降机会；尚不能确认普遍优于 SWX、达到手写性能或具有全局最优性。最有价值的下一步讨论，是把这些成立条件与预期程序形态对齐，再由实际生成代码检验收益。
