# 第 6 讲：值、存储与生命周期

[上一讲](05-dataflow.md) · [课程目录](README.md) · [下一讲](07-layout.md)

本讲目标：区分实例身份、当前值、数据来源与目标位置，并识别覆盖危险。

## 1. 四个不同的问题

| 概念 | 例子 | 回答的问题 |
| --- | --- | --- |
| 实例身份 | hdr.a | 我们讨论哪个逻辑对象？ |
| 当前值 | 修改后的 count | 程序现在观察到什么？ |
| 物理来源 | 原缓冲区 `[0, 4)` | 可以从哪里取得字节？ |
| 目标位置 | 输出 `[2, 6)` | 最后需要放在哪里？ |

这些信息可以相关，却不能合并成一个永远不变的指针。头部移动后，旧指针可能指向别的内容；字段修改后，原字节可能不再代表当前值。

## 2. 延迟物化

提取 A 后，可以保留原报文视图，按需读取字段。若只有一个字段被修改，可以记录该字段的新值，其他字段继续来自原报文，最后构包时合成结果。

一种教学表示是：

```text
HeaderValue {
    original_region
    changed_fields
    validity
}
```

它只说明一个设计方向。真实实现还要处理新建 header、运行时长度和初始化状态。记录了“某字段变脏”之后，所有后续字段读取都必须优先读取新值，否则解释语义会前后矛盾。

物化指把这种逻辑表示实际写入一段存储。延迟物化可能减少复制，但会增加读值分派或状态管理，收益需要测量。

## 3. 定义、使用与活跃性

一个值的定义产生它，使用消费它。若某个旧值未来仍可能被使用，它就是活跃的。

例如先读 A.count，随后修改 A.count，最后还要使用先前读出的标量值；旧值仍然活跃，但可以保存在局部变量中，并不要求整个 A 的旧字节都保留。

反过来，header 不再 emit，也不保证它的字节立刻可覆盖：后续计算仍可能读取字段。安全释放或覆盖时机由全部使用决定，不能只看输出列表。

## 4. 别名与内存依赖

两个视图若覆盖同一缓冲区的相交区间，就存在重叠。例如 `[0, 4)` 与 `[2, 6)` 重叠，`[0, 2)` 与 `[2, 4)` 不重叠。

不同逻辑名字也可能引用同一来源；相同的数字偏移若属于不同缓冲区，则不一定重叠。因此区间必须携带缓冲区身份。

调度通常关注三类约束：先写后读保证读到新值；先读后写避免旧值被破坏；两次写入的先后保证最终值正确。报文搬移常见的危险是先读后写依赖被颠倒。

## 5. 对 v0 的意义

v0 在 deparser 统一提交物理重构，给分析提供了清晰边界：先确定仍需哪些值，再计划覆盖原存储。但“统一提交”不自动保证安全；guard、字段值和来源区间仍可能依赖将被覆盖的字节。

v0 暂不支持某些旧值发射和重复 emit 情形，可以缩小值版本问题的范围。不要因此假设所有来源天然互不重叠。

## 练习

A 的源区间是 `[0, 2)`，B 的源区间是 `[2, 4)`。计划先将 A 写到 `[2, 4)`，再读取 B 来计算一个输出字段。这安全吗？给出两种修正方法。

## 参考答案

不安全：A 的写入破坏 B 的旧值。可以先完成对 B 的读取与计算并保存结果，再移动 A；也可以先备份 B，再让后续计算读取备份。若计算有副作用或其他依赖，提前计算还必须保持这些约束，不能随意跨越操作。
