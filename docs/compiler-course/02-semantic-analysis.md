# 第 2 讲：从 AST 到语义表示

[上一讲](01-semantics.md) · [课程目录](README.md) · [下一讲](03-ir-design.md)

本讲目标：理解语法树还缺少什么信息，以及为什么 planner 不应该反复查名字或猜测位宽。

## 1. AST 保留表达形式

考虑字段赋值：

```text
hdr.a.count = hdr.a.count + 1
```

AST 可以表达“赋值、成员访问、加法、整数常量”，但仅凭这些节点，还不知道 `hdr` 绑定到哪个参数、`a` 属于什么类型、`count` 的位宽，以及右侧运算结果如何转换成目标类型。

语义分析应将这些问题解决，或对不支持的情况报告诊断。解析成功并不意味着程序能合法运行。

## 2. 名字解析与符号身份

符号表记录名字对应的声明。作用域决定当前查找应使用哪个声明。两个不同作用域中的同名变量可能是两个完全不同的对象。

解析完成后，可以用稳定的内部 ID 表示引用：

```text
FieldRef {
    instance_id: 3
    field_id: 1
    type: Bits(16)
}
```

这是教学数据格式。实际实现可以使用索引或其他句柄；关键在于后续阶段不再依赖字符串拼接判断身份。仍应保留源位置，用于报错。

## 3. 类型与布局不是一回事

`Bits(16)` 说明值有 16 位，并不意味着可以直接把报文地址转换成宿主机 `uint16_t*`。网络字节序、地址对齐和 C 的访问规则仍需要后端处理。

对于 v0 的字节对齐定长字段，假设 A 包含 8 位的 tag 和 16 位的 count：

| 字段 | 逻辑类型 | 线格式字节偏移 | 字节长度 |
| --- | --- | --- | --- |
| tag | Bits(8) | 0 | 1 |
| count | Bits(16) | 1 | 2 |

这个线格式不依赖 C struct 是否插入 padding。不要直接用 `sizeof` 某个宿主结构体代替报文长度。

## 4. 常量求值与显式转换

常量求值可以提前确定类型宽度、固定长度和恒定条件，但必须采用源语言的算术规则，而非无意使用宿主语言规则。

在一个已明确按 8 位无符号模运算的教学表达式中，`255 + 1` 得到 0。真实 P4 表达式还要先确定操作数类型、常量规则和转换是否合法，不能对所有加法一律套用这个例子。

一种有用的 IR 约定是显式表示运算位宽和必要转换，让后端不必推断。例如 `AddBits(8, x, y)`；对不支持的宽度应明确拒绝或选择已定义的实现。

## 5. 阶段边界

离开语义分析时，至少应知道：每个引用对应什么声明、表达式结果类型、支持的调用含义、常量的值，以及发生错误时的源位置。

现有 [sem.c3](../../src/sem.c3) 提供索引和子集检查，可以作为阅读入口；它不等于已经完成这里描述的类型分析。对 v0 之外的程序给出诊断，也是一项正确性要求。

## 练习

1. 两个实例 A、B 使用同一个 header 类型，它们的 count 字段可以只用同一个 field_id 区分吗？
2. 上述 3 字节 header 能否直接按一个可能占 4 字节的 C struct 复制？
3. 给 FieldRef 增加一项信息，使后端报错时能定位源程序。

## 参考答案

1. 不可以。字段定义可以共享，但字段引用还需要实例身份，否则 A.count 与 B.count 会混淆。
2. 不能据此直接复制。线格式是 3 字节，宿主结构布局可能包含 padding，还可能涉及字节序差异。
3. 增加 source_location 或指向源 token 的信息。诊断信息应随转换保留，而非等后端出错再猜来源。
