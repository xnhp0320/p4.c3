# 第 3 讲：设计第一套 IR

[上一讲](02-semantic-analysis.md) · [课程目录](README.md) · [下一讲](04-control-flow.md)

本讲目标：能为一个 IR 操作写出含义、输入输出、前提和验证规则。

## 1. IR 是一套内部语言

IR（Intermediate Representation，中间表示）不只是若干结构体。它还包括每个操作的语义，以及合法程序应满足的规则。

设计时从下游要做的事情反推。例如，planner 需要知道输出区间的来源和顺序，就应当能直接获取这些信息；不应每次都重新遍历各种源语法。

## 2. 从一个小操作集合开始

下面是一套教学语义操作：

| 操作 | 含义 |
| --- | --- |
| Extract(h, n) | 从 cursor 提取 n 字节到 h，成功后推进 cursor |
| ReadField(h, f) | 取得字段当前逻辑值 |
| WriteField(h, f, v) | 更新字段当前逻辑值 |
| SetValid(h, b) | 设置有效性，不直接移动报文 |
| Emit(h, guard) | 在该输出点按 validity 和 guard 选择当前内容 |
| Accept / Reject | 结束 parser 路径 |

这不是完整的 v0 IR。分支、stack、varbit 和 extract_end 需要逐步加入，但不必为了未来所有功能一次设计完毕。

以 Extract 为例，需要明确：n 的单位为字节；读取范围必须存在；成功时更新值与 validity；失败进入约定的 reject 路径；不允许把失败后的部分状态当作成功输出。实现还需要准确遵守项目选定的提取语义。

## 3. 归一化应保留求值含义

`emit(h)` 与 `if (h.isValid()) emit(h)` 可以在适当条件下归一化为相同的输出选择。显式 guard 则必须在语义允许的时刻求值，并保持无副作用等子集约束。

不能仅因为 guard 是一个布尔表达式就随意提前计算。若它引用的字段稍后被修改，提前计算可能得到不同结果。教学上的 `Emit(h, guard)` 表示在该输出点观察 guard 和当前值；后续移动计算位置必须有依赖分析支撑。

## 4. 不变量与 verifier

不变量是每份合法 IR 都应满足的条件，例如：

- 所有 instance_id 和 field_id 都存在，且彼此匹配。
- 字段写入的值类型符合该字段要求。
- 每个控制流目标都存在。
- v0 输出实例不重复出现，输出形式符合子集限制。
- 偏移与长度单位明确，不混用 bit 和 byte。

IR verifier 检查这些结构约束。它能发现编译器内部错误，但不能单独证明整个转换保留语义。后者仍需要推理、测试和阶段对照。

## 5. 多阶段表示

语义 IR 表达程序动作；布局 IR 表达输出内容和位置；执行计划表达移动、保存和写入。初期可以用小型结构体集合实现这些阶段，不必依赖大型框架。

每个阶段都应能 dump 成可读文本。例如错误输出时，可以分别检查“选错了 header”“算错了位置”“移动顺序错了”，而不是只面对一大段 C。

## 练习

设计 `Move(dst, src, len)` 的约定，回答：地址属于什么缓冲区？是否允许重叠？如何表达执行顺序？谁负责证明范围有效？它适合语义 IR 还是执行计划？

## 参考答案

一种合理设计使用缓冲区身份加字节偏移表示地址，允许单次操作内部重叠并采用 memmove 语义；操作按计划顺序执行。planner 必须提供范围和依赖依据，运行时对动态容量作检查。它适合执行计划，因为它已经选定了物理实现。

只写三个整数而不说明所属缓冲区、单位与顺序是不够的；这些约定缺失时，即使代码能运行，也难以验证其正确性。
