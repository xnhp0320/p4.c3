# 第 9 讲：Lowering 与 C 生成

[上一讲](08-scheduling.md) · [课程目录](README.md) · [下一讲](10-validation.md)

本讲目标：将语义、布局和执行步骤分阶段转换，理解生成 C 时仍要保留的约束。

## 1. 逐步作出决定

Lowering 将较高层的领域操作转换成更明确的实现：

```text
语义：输出 A、C 和剩余 payload
布局：计算来源、长度和目的位置
计划：检查容量，准备值，移动 A，提交起点和长度
C：局部变量、分支、memmove 和运行时接口调用
```

每次转换应说明消除了什么抽象、保留什么约束。不要在输出 C 字符串时重新决定复杂的布局策略，否则很难独立验证。

## 2. Parser 的直接生成

状态可降低为 label/goto。每次提取仍检查长度，成功后推进 cursor，失败跳到 reject。以下是 C 风格示意，不是完整可集成后端：

```c
parse_a:
    if (cursor > input_len || need > input_len - cursor) {
        goto reject;
    }
    /* 记录或读取 input[cursor .. cursor + need)。 */
    cursor += need;
    goto parse_next;
```

短路求值避免 cursor 超界时执行可能下溢的减法。need 的来源、类型范围和实际读取方式也必须受约束。不能在检查之前先读取对应字节。

## 3. 字段访问

逻辑值不能直接等同于宿主 struct。后端要处理网络字节序、未对齐访问、整数位宽、移位边界与溢出。

读取 16 位网络字段可以使用字节组合，或复制到适合的临时对象后转换字节序。不能仅因地址可访问，就假定转换成整数指针后解引用一定合法。

修改字段后，后续读取必须观察当前逻辑值，输出时按线格式写回。不支持的宽度应明确拒绝，不能静默缩窄到宿主整数。

## 4. 运行时接口

教学后端可区分成功、源程序 reject、资源或目标条件不满足、编译器内部错误。名称可由项目决定，但不能全部冒充短包 reject。

项目 direct-mbuf 快路径依赖独占可写、parser 消费前缀连续、增长空间足够等条件。失败时必须进入已定义的回退。

单次提交不自动具有事务性。一种便于推理的策略是：先完成可能失败的检查与必要分配，再执行内存写入，最后更新报文起点和长度。若写入阶段仍可能失败，需要明确如何处置部分修改状态。

## 5. 下游 C 编译器的职责

C 编译器可以完成指令选择、寄存器分配和通用优化。P4 后端仍负责源语言语义、布局和内存调度；这些信息若提前丢失，不能指望下游自动恢复。

第一版可先生成直白、便于审查的代码，验证正确后再消除重复计算、合并搬移、专门化常见路径。每种优化都应有明确适用条件。

## 练习

为“删除 B，移动 A，保留 C 和 payload”排序：更新元数据、检查目标空间、确定选择条件与字段值、执行移动。若 guard 读取 B，为什么不能移动后再计算？

## 参考答案

一种顺序是：在正确语义时刻确定条件和字段值，计算布局并检查目标空间，准备临时存储，执行安全移动与写入，最后更新元数据。独立检查可以提前，但不能破坏依赖和失败约定。

A 的移动会覆盖 B 的原区间，之后从原位置读取 guard 可能观察到 A 的字节。应提前取得结果，或保存 guard 所需的旧值。
