# 第 8 讲：搬移依赖与调度

[上一讲](07-layout.md) · [课程目录](README.md) · [下一讲](09-codegen.md)

本讲目标：识别多次移动之间的覆盖依赖，并解释何时需要 scratch。

## 1. memmove 的保证有边界

单次 memmove 允许源与目的区间重叠，其效果如同先保存源字节再写入目标。但它不保存其他调用未来需要的字节。

考虑同一缓冲区中的两个操作：

```text
M_a: [0, 2) -> [2, 4)
M_b: [2, 4) -> [4, 6)
```

先执行 M_a，会覆盖 M_b 的来源。正确顺序是 M_b、M_a。即使两次调用都使用 memmove，错误顺序仍会得到错误输出。

## 2. 建立依赖图

对移动 M_i 记录读区间 R_i 和写区间 W_i。若 W_i 与另一个操作的 R_j 重叠，且 R_j 仍要求原值，就加边 M_j -> M_i，表示 M_j 必须先执行。

若图无环，拓扑排序能给出合法顺序。一个操作自己的重叠由 memmove 处理，不要因此添加自环。新字段写入也可能覆盖别人的来源，必须参与调度。

若输出目标彼此重叠，还需明确写入先后和最终值；最小布局 IR 可以先禁止最终片段互相覆盖。

## 3. 依赖环与备份

交换两个相邻的 2 字节区间时：

```text
M_a: [0, 2) -> [2, 4)
M_b: [2, 4) -> [0, 2)
```

两个方向都有依赖。一种执行方案是：先将 `[0, 2)` 备份到 scratch，再把 `[2, 4)` 移到 `[0, 2)`，最后将 scratch 写到 `[2, 4)`。

备份改变了 M_a 的来源，因而打破依赖环。这个算例用于说明一般原理；header 重排快路径不属于当前 v0 必做范围。

一般情况下，scratch 大小取决于需保存的活跃来源，不能从例子推断“一个 header 的空间永远够用”。初期可以采用容易验证的完整 gather 回退，再逐步优化。

## 4. 同序区间的简化策略

在以下前提下，项目的同序构包可以使用简单调度：源区间互不重叠且依次排列；目标区间互不重叠并保持同序；每个保留区间的源、目标长度相等；没有其他需要保存的旧值或别名。

- 向左移动的区间，按源位置从左到右处理。
- 向右移动的区间，按源位置从右到左处理。
- 新增内容在相关旧来源安全移动或保存之后写入。

这些前提排除了相反方向之间的破坏性覆盖。字段修改、变长内容等应先拆成满足前提的片段，或进入更一般的路径。

它不是任意区间集合的通用排序规则。来源重复、输出重排和额外旧值使用都需要重新判断。

## 5. 动态位置

若位置依赖运行时 guard 或长度，编译器可能无法构造完全静态的依赖图。可以证明某类布局始终符合充分条件，生成有明确入口谓词的专用路径，或回退到独立 scratch 构造。

回退也需要容量和失败约定。优化与回退应产生相同逻辑输出，资源不足如何报告则由运行时接口定义。

## 练习

X 从 `[0, 2)` 移到 `[2, 4)`，Y 从 `[2, 4)` 移到 `[4, 6)`，Z 从 `[4, 6)` 移到 `[6, 8)`。给出依赖和合法顺序。若先写新字段到 `[4, 6)`，会破坏什么？

## 参考答案

依赖为 Z -> Y、Y -> X，顺序为 Z、Y、X。先写新字段会破坏 Z 的来源；该区间还是 Y 的最终目标，若新字段属于最终输出，布局本身还有目标冲突，需要先修正或定义覆盖语义。
