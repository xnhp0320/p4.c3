# 项目动机、目标与第一阶段产出（初稿）

> 本文记录当前的项目定位和第一阶段交付范围。具体实现路线、包构造 planning 方案与 roadmap 由后续讨论确定。

## 项目定位

本项目要实现一个**基于 DPDK 的高效 P4-to-C 代码生成器**：以 P4 对报文格式、解析、处理和反解析的描述为输入，生成可集成、可验证、性能可衡量的 C 代码。直接生成 C3 也是可考虑的后端方向；现阶段不把输出语言的选择当作核心技术问题。

**面向 DPDK 的代码生成是明确的项目目标，DPDK 是当前唯一 target。** 当前的布局、解析与构包优化围绕 DPDK 报文处理环境展开；kernel、eBPF 等其他 target 留待后续考虑，不纳入当前实现范围。C 与 C3 是输出语言的选择，二者都可以面向 DPDK。

P4 是输入语言的起点，项目后续会根据软件报文处理与代码生成的需要扩展 P4。当前偏好沿用本项目的轻量前端，不预设依赖官方 p4c；如果后续证明复用 p4c 能明显简化实现，也保留采用它的可能。前端选择与是否复用 DPDK SWX 是两个独立决策，使用 DPDK 本身不要求采用 SWX。

项目的主要研究对象是软件报文处理，尤其是自定义报文结构的解析与处理后的重新构造。重点不止于把 P4 语法翻译成 C 语法，而在于保留 P4 语义的同时，规划内存访问、报文布局和数据移动。第一阶段最关键的挑战是 deparser 的 packet build：减少不必要的内存复制，使生成代码的性能接近手写实现。

## 为什么使用 P4 作为输入语言

1. **报文生命周期的描述能力。** Header 类型可以描述自定义报文布局；parser 状态图可以描述识别、提取和协议分派；处理逻辑可以修改 header 与 metadata；deparser 可以描述输出 header 的次序和条件。这些结构为“读取原报文 → 处理 → 构造新报文”的代码生成提供了共同的语义输入。
2. **受约束的处理模型。** P4 避开了 C 中常见的裸指针操作和通用控制循环，让许多报文处理步骤以 parser、table、control 和 deparser 的形式显式出现。这有利于分析数据边界、状态和依赖。但 parser 状态图允许回边，不能把 P4 简化为“没有循环”。
3. **表的模块边界。** Table 声明给出 key、匹配方式和可执行的 action 集合，更像查找接口或契约，而不规定软件查找结构的具体实现。这为将业务描述与后端的表实现分离提供了基础。“类似 IDL”只用于说明这层接口性质；action 的具体行为仍由 P4 程序定义。
4. **扩展入口。** Extern 为目标相关能力提供接口，annotation 可附加编译器或目标需要的元信息。项目可以借助这些机制表达软件后端的能力与约束，也允许按需求扩展语法或语义。扩展需要说明含义、与现有 P4 行为的关系，以及对代码生成的影响；具体扩展集合待后续讨论。

上述是项目采用 P4 的动机，也是后续实现要检验的假设；语言表达能力本身不能证明生成代码的正确性或性能。

## 第一阶段要解决的问题

### 1. 包头格式转换

把 P4 header 描述转换为生成代码可用的数据布局与字段访问方式，正确处理字段位宽、有效性、可变长度和字节序。生成结果需要区分“逻辑字段”与“原始报文字节”，并明确安全读取和写入的边界。

### 2. 包解析器 codegen

将 state 和 transition 直接翻译为 C label/goto 是可用的状态机实现。重点是为 `extract`、`lookahead`、`advance` 选择合适的数据表示与读取方式，在保留边界检查和错误行为的同时，避免不必要的整头复制与字段加载。已有的 OVS 提取实验可以作为解析侧的研究样例，但它还没有证明代码生成或行为等价。

### 3. 包 deparser 的 codegen

P4 deparser 描述的是输出内容与顺序，例如按 header 有效性执行 `emit`；它没有直接指定软件后端应如何分配输出空间、安排写入位置、复用原报文数据或处理长度变化。代码生成器需要将这种逻辑描述变成具体的 packet build 计划。

这个计划至少要回答：输出长度和布局何时可确定，原 payload 如何衔接，header 插入、删除和改写如何影响偏移，条件输出如何安排写入，哪些字节可以复用或原位修改，以及何时必须搬移或复制。还要处理越界、溢出、重叠内存和失败路径。核心目标是在这些约束下减少内存复制，使生成的构包代码接近手写代码的性能。这里先界定问题，不预设某一种零拷贝或两遍构造方案。

需要联合分析 parser 的数据来源、中间处理的读写与 deparser 的输出布局，选择直接改写、局部移动、必要备份等代码路径，并规划临时空间和输出空间。已有 T4P4S 与 DPDK SWX 已包含指针式提取及低复制构包机制；本项目的进一步优化空间需通过具体程序和性能对照来验证。详见 [已有实现调研](codegen-research.md) 与 [技术挑战梳理](parser-deparser-challenges.md)。

“高质量”在这里至少包含四个可分别验证的维度：语义正确、内存安全、性能接近手写实现、生成代码便于审查和集成。性能比较需要使用相同报文行为与工作负载；具体基准留待后续讨论。

## 第一阶段产出

以下三项能力共同组成面向 DPDK 的代码生成能力，生成的报文处理代码需要能够在 DPDK 环境中集成和验证：

- **包头格式转换能力：** 从 P4 header 描述生成软件侧的布局与字段访问代码。
- **包解析器 codegen：** 从 P4 parser 生成可执行的报文解析代码。
- **包 deparser codegen：** 从 P4 deparser 生成可执行的报文构造代码，并重点优化内存复制与数据移动，使其性能接近手写实现。

这些产出需要通过报文级正确性检查和与手写实现的性能对比来检验。设计文档和独立语义 spec 不列为第一阶段交付项；实现中必须明确的语义约束仍需在代码与测试中落实。直接 P4-to-C3 是否纳入后续阶段，待实验后决定。

## 当前状态与后续讨论边界

仓库目前有 P4_16 子集的词法、语法解析和 AST 输出，还没有类型检查、针对 deparser 的语义处理或代码生成器。现有 [OVS miniflow 提取实验](ovs-miniflow.md) 主要考察 parser 的表达成本，不能充当 packet build 的验证。

当前路线沿用自己的简易前端，围绕项目需求补齐语义并面向 DPDK 生成 C/C3。接下来的讨论应细化报文构造 planning，再决定 IR、运行时接口和实验顺序。SWX 首先是通用报文指令解释器，另有可选原生 codegen 加速；其存储与构包机制可作为参考，但采用其 spec 意味着接入相应执行模型，不能直接等同于本项目的专用代码生成。相关职责边界见 [p4c-DPDK → SWX spec 深入调研](swx-spec-pipeline.md)。本文不提前制定 roadmap。
