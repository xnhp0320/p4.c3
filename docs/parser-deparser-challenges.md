# Parser / deparser C codegen：数据表示与构包规划

本文细化第一阶段的技术挑战和可研究方案。已有实现的源码证据见 [软件后端调研](codegen-research.md)。下面的存储表示、分析方法和成本模型是讨论候选，尚未实现，也不构成已确定的 IR、语义 spec 或 roadmap。

2026-09-28：关于静态公共顺序、运行时 packet ctx 数组与 action 边界提前重构的具体方案，见 [与 SWX 的比较及设计评估](incremental-header-rebuild-evaluation.md)。该文补充复制成本、循环区域、提交时机和未来重排的边界。

核心问题是：**在保持 P4 可观察行为的前提下，利用程序信息决定何时读取、保存、改写和移动报文字节，使常见路径接近手写代码的成本。** Parser 与 deparser 必须共享这些信息。

## 1. Parser 状态机与 extract 是两层问题

State 可以直接成为 C label，transition 可以成为 goto 或条件跳转。p4c-uBPF 已采用这种翻译。是否进一步把某个循环区域恢复为 while，可以服从代码质量和性能需要；label/goto 本身不必视为性能缺陷。

`extract` 则包含读取字段值、设置 validity、推进 cursor，以及处理长度不足等行为。可变长度 header 还要记录实际位宽。P4 描述这些结果，没有要求逐个 header 分配堆内存或执行整头 memcpy。见 [P4_16 v1.2.5 §13.8](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-packet-data-extraction)。

生成器需要选择如何实现这一逻辑操作：

| 表示方式 | 成本和适用条件 |
| --- | --- |
| 标量字段 | 按需加载到 C 局部值，便于计算和复用；未使用的字段不必解码 |
| 原报文视图 | 保存来源偏移、长度等，字段按需读取；没有整头物化成本，但必须跟踪写入和生命周期 |
| 独立 header 存储 | 用于新头、必须保留的旧版本、无法直接访问的跨段数据等；需要控制大小和存活期 |
| 混合表示 | 保留原始字节区间，只将参与计算或修改的字段物化；其余字节直接保留或按区间移动 |

这里的描述符首先是编译器要知道的信息，不要求最终 C 为每个 header 都保留一个运行时结构。静态偏移和长度可以直接折叠到生成代码里。

按需提取还有两个容易混淆的边界：未被 control 读取的字段可能仍需随 header 发射，必须保留其字节；即使整个 header 最终不使用，extract 的 cursor、短包错误等行为也不能直接删除。只有证明这些行为不再可观察，才能进一步消除。

## 2. 原报文指针必须保持 P4 的值语义

Header 赋值复制字段及 validity；它不会把两个 P4 header 变成共享可变对象。`emit` 按执行时的有效性和内容追加输出。见 [header 操作](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-ops-on-hdrs)、[deparser 语义](https://p4.org/wp-content/uploads/sites/53/2024/10/P4-16-spec-v1.2.5.html#sec-deparse)。由此得到两个直接约束：

```p4
hdr.saved = hdr.original;
hdr.original.field = new_value;
```

若后续还读取或发射 `saved` 的旧字段，不能简单令两个 header 指向同一块可写内存。可以只保存仍然活跃的旧字段，也可以使用独立存储或延迟写回；是否需要整头复制，要由后续使用决定。

```p4
packet.emit(hdr.h);
hdr.h.field = new_value;
packet.emit(hdr.h);
```

如果目标允许这样的 deparser，两个输出位置可能需要不同版本。只在运行时记录两次同一个可变指针、最后统一复制，会丢失第一次 emit 的值。生成器需要记录版本或在写入前完成必要输出。若选用受限 deparser 子集，也必须明确检测不支持的程序。

因此，原位改写的证明条件至少包括：原始值已无后续使用，不会改变其他逻辑 header 的值，不会覆盖未来 emit 的来源，也不违反 extern 或宿主对输入报文的观察约定。`setValid()` 不代表所有字段已经初始化；新 header 的字段定义情况仍需跟踪。

## 3. 先建立输出布局，再安排内存操作

可将一次实际执行的输出理解为一串带有来源、版本、长度和条件的区间：原报文字节、新生成字节、修改后的字段，以及由软件目标契约确定的 payload。布局分析应贯通 parser → control → deparser；仅比较 parser 与 deparser 的 header 名字和次序不够。

对采用“输出 header 后接 parser 剩余 payload”的软件目标，考虑以下候选策略：**固定 payload 的物理位置，调整报文起点，只移动必要的前缀。** 这是一个目标契约下的优化策略，不是 P4 语言强制规定的 packet I/O 模型。

设所有量均已安全换算为字节：

```text
S = 输入报文起点
I = parser 消费的输入长度（包括 advance）
O = deparser 输出的 header 总长度
P = S + I                       原 payload 起点
S' = P - O = S + I - O           候选输出起点
```

若空间、所有权与连续性满足要求，payload 可以留在 `P`。增长量 `O-I` 为正时消耗 headroom；为负时向后调整报文起点。编译器还需决定哪些旧字节留在原位、哪些移动到 `S'` 前缀内。

`I` 不能用“最终存活 header 的长度之和”替代：advance、重复 extract 到同一变量、局部工作 header 都可能使两者不同。被跳过的输入也不能因为还在内存里，就自动成为输出。非字节对齐输出则需单独的位级处理，不能套用这里的字节公式而截断。

### 典型变换及其候选成本

下表中 `P` 是保持不变的 payload，`N` 是新生成 header。假定相关区域可写、所需数据连续、容量足够，且旧值生命周期允许这些操作；表内成本是推导，不是测量结果。

| 输入 → 输出 | 候选生成策略 | 主要数据移动 |
| --- | --- | --- |
| `A B P → A B P`，只改少数字段 | 直接写对应字段，或延迟到最终位置写入 | 无需重建其余 header 和 payload |
| `A B P → B P` | 调整报文起点及长度 | 无字节复制 |
| `A B P → N A B P` | 在 headroom 构造 N，再调整起点 | 写入 N，旧报文无需复制 |
| `A X B P → A B P` | A 向右移入被移除的空间，B/P 不动 | 移动 A，必要时合并字段改写 |
| `A B P → A N B P` | A 向左移动，为 N 留空，B/P 不动 | 移动 A 并写入 N |
| `A B P → B A P` | 局部旋转，必要时用 scratch 打破覆盖依赖 | 移动 A/B，payload 不动 |
| `A P → A A P` | 保留可复用的一份，在另一位置生成副本 | 需要新增输出字节；不等于必须复制整包 |

例如 `A(14B) X(4B) B(20B) P` 删除 X 时，令 `S'=S+4`，用 `memmove(S+4, S, 14)` 保存 A 的布局，B/P 原位保留。反向插入 4B 新头时，在足够 headroom 下令 `S'=S-4`，将 A 左移 4B，再写入新头。二者都只移动短前缀，与 payload 长度无关。

这些是抽象 header 的布局例子。若实例是 VLAN 插入/删除，EtherType 等字段还须按 P4 action 的结果写入。进一步分析这些覆盖写，可能连前缀内即将被覆盖的字节也不必复制；布局规划与字段写入融合才有机会接近手写实现。

### 重排不等于重新分配整包

对连续的 `A B → B A`，可以先将较短的一段保存在临时区，使用 memmove 移动另一段，再恢复临时段。简单策略的临时空间为 `min(|A|, |B|)`，数据搬运量为 `|A|+|B|+min(|A|, |B|)`；常量小头还可能由少量寄存器暂存。它不要求新建完整 packet buffer，也不承诺是所有 CPU 上最快的策略。

一般情况需要针对内存区间建立依赖：若操作 U 的写入会覆盖操作 V 尚未读取的源，则 V 必须先于 U，或者必须先保存那部分源。还要将新 header 写入和字段覆盖写纳入同一分析。单次 memmove 只解决该次调用的重叠问题，不能保证多次移动组成的序列安全。

对于依赖环，可以拆分区间或引入 scratch。需要保存多少字节取决于实际覆盖与存活关系；不能直接假设“所有 header 都要备份”，也不能无条件假设“一个最大 header 的临时区就够”。

## 4. 静态分析需要回答什么

| 分析对象 | 需要的信息 | 决定的代码生成行为 |
| --- | --- | --- |
| Parser 路径 | 来源偏移、实际位宽、cursor、循环与错误出口 | 建立原报文视图，保留必要检查 |
| 字段使用 | 读写集合、最后使用点、需要保留的旧值 | 按需加载、消除冗余转换、确定写回时机 |
| Header 值 | 赋值、有效性、初始化、来源和版本 | 判断能否共享只读来源、何时需要物化 |
| Deparser 路径 | emit 次序、条件、重复发射、当时值版本 | 计算输出区间和总长度 |
| 区间关系 | 源/目的重叠、连续性、覆盖依赖 | 合并移动、消除移动、安排顺序和备份 |
| 存储生命周期 | scratch 峰值、新头存活期、是否跨线程/队列 | 决定栈、上下文、mbuf 私有区或其他存储 |

字段偏移、固定头长度、部分依赖可在编译期确定；validity、varbit 长度、table action 选择和实际 headroom 往往需要运行时值。合理目标是静态生成可证明的快路径，把必要的少量条件保留为 guard，并为其他情况保留正确的通用路径。

这还包含代码体积的取舍：为每一种 parser 路径与 header 有效性组合展开完整构包代码，可能造成分支和指令缓存成本。需要在专用路径、共享片段和通用处理之间选择，不能只按复制字节数评价“最优”。

中间处理的影响不可忽略。即使第一阶段聚焦 parser/deparser，也需要知道 control 或外部处理会读写哪些 header、是否新增/删除 header、是否保留原数据引用。未知副作用应成为优化边界；这些信息的获取方式仍待设计。

## 5. DPDK 内存位置：headroom 与元数据区要分开

通常直接 mbuf 的布局可示意为：

```text
[ rte_mbuf 元数据 ][ 可选 private area ][ data buffer                         ]
                                         [ headroom ][ packet data ][ tailroom ]
                                                      ↑ data_off
```

Headroom 是数据缓冲区中当前报文起点之前的空间，`rte_pktmbuf_headroom()` 返回 `data_off`。它与 `rte_mbuf` 自身的元数据、private area 是不同区域；外部/间接 buffer 的物理布局还会不同。见 [DPDK mbuf 文档](https://doc.dpdk.org/guides/prog_guide/mbuf_lib.html)、[headroom 与 private area API](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/mbuf/rte_mbuf.h#L278)。

对于输出新增的前缀，headroom 值得优先利用。对于少量临时值，寄存器或有界栈空间可能更合适；“不逐包堆分配”不等于“所有 scratch 都放 headroom”。

| 位置 | 适合存什么 | 规划时的约束 |
| --- | --- | --- |
| 寄存器 / 小型栈空间 | 少数字段旧值、短区间交换 | 存活范围、寄存器压力、栈上界 |
| Mbuf headroom | 最终输出的新前缀；可证明空闲的临时区 | 不能与输出目标或尚未读取的来源冲突；空间必须足够 |
| Mbuf private area | 随 packet 存活的编译器状态、小型工作区 | 由 mempool 创建配置提供；跨 clone/队列时需明确生命周期 |
| 预分配执行上下文 | 较大或可复用的 scratch | 不能被同一 lcore 上多个未完成 packet、重入调用覆盖 |
| Mempool 中的新 mbuf/segment | headroom 不足或输出布局需要独立存储 | 分配和链表成本、TX 对多段报文的支持 |
| 通用堆分配 | 特殊慢路径候选 | 避免成为正常逐包路径的必要步骤 |

新增前缀占用的 headroom 和 scratch 如果同时存活，应分配互不重叠的区间；只有证明生命周期不重叠才能复用。同样，去掉的旧 header 空间在其值已不再使用后，可能成为临时空间候选。

`rte_pktmbuf_prepend` / `adj` 修改的是起点和长度，不能自动完成中间插入、删除或重排，也不自动保证独占写权限。前者要求首段 headroom 足够，后者受首段长度限制。见 [对应实现](https://github.com/DPDK/dpdk/blob/4f795ddd6a1fbdea97b7b254dea6d8f1f837a681/lib/mbuf/rte_mbuf.h#L1670)。

## 6. 影响代码质量与正确性的边界

- **连续性：** 整包 `pkt_len` 足够不代表某个 header 在当前 segment 中连续。需要跨段读取、局部物化或明确的入口条件；不能仅凭总包长形成可解引用的连续指针。
- **所有权：** Clone、间接或外部 buffer 可能共享数据。原位写入依赖可写性保证；条件不成立时应选择复制或独立输出路径。
- **位布局：** C bitfield 的布局、对齐和字节序不能直接代替 P4 wire layout。还需避免越界宽加载、未对齐访问和别名规则带来的未定义行为。
- **动态长度：** 长度加减、位到字节换算和目的偏移必须防溢出；读取较少字段不能省略 P4 要求的整体 extract 检查。合并检查也不能改变可观察的错误和部分结果。
- **失效与失败：** 移动或重新分配 buffer 后，原指针可能失效；开始破坏源数据前，应完成必要容量检查或准备恢复路径。不能到重排中途才发现临时空间不足。
- **运行时边界：** Extern、克隆、队列和再次解析可能使原数据或中间状态继续可见，限制延迟写回与存储复用。
- **宿主元数据：** 输出变化可能影响 `data_off`、长度、分段以及 TX offload 的层偏移。协议长度、校验和按 P4/extern 定义计算，不能靠 memcpy 自动修正。

这些边界不意味着第一阶段必须一次支持全部情况；需要为最终选择的支持范围生成正确代码，并对范围之外的输入或程序明确处理。

## 7. 如何检验“接近手写性能”

比较应固定输出行为、短包检查、所有权与 segment 假设，记录编译器、优化选项、CPU、DPDK 版本和 packet 工作负载。参考对象包括手写 C、T4P4S、SWX 生成的原生 C 路径；只与 SWX 解释路径比较不足以证明代码生成优势。

候选场景包括原样转发、少数字段改写、外层封装/解封装、中间头插入/删除、不同长度的 header 交换，以及带动态长度和条件 emit 的组合。正确性用例还要覆盖旧值保留、重复 emit、headroom 不足和所支持的跨段情况。

除吞吐率外，至少区分：每包复制的 header 字节与 payload 字节、分配次数、scratch 峰值、cycles/packet、分支及 cache 成本、生成代码体积。先观察生成 C，再检查优化后的机器码；更少 memcpy 调用不一定意味着更少数据搬运或更快执行。

目前可提出的研究假设是：**通过联合分析 header 来源、值版本、输出布局和内存约束，针对常见程序生成少复制、少 bookkeeping 的构包代码。** 它是否胜过已有运行时快路径，以及优势出现在哪些报文变换上，需要实现和测量回答。
